# 验收、证据与演示

## 完成标准

1. 两个工作流画布已创建，并保存实际链接/版本。
2. 知识库只含3条规则，检索运行确实召回3条完整policy。
3. 单条输出结构和中文报告一致，客服证据确实来自相应agent消息。
4. 三种核心记录通过：正常、明确违规、缺资料转人工。
5. 批量复用单条，能输出统计和逐条待复核清单；总数与输入一致。
6. 已执行data/eval_inputs.json中的样例，实际结果保存在verification/actual_results.json，人工复核语义判断。
7. 保存至少一张完整画布截图、一条正常结果、一条违规证据、一条复核结果及批量汇总。不要用本地夹具报告冒充平台截图。

## 推荐的错误注入

| 场景 | 预期 |
|---|---|
| 删除/取消选择规则R03，再运行 | 进入rule_coverage_error人工复核，不输出三项通过 |
| 在测试副本里令模型输出不是JSON | 03_validate生成复核结果，不进入普通分流 |
| 将模型候选中的客服quote改成不存在的原文 | 输出unknown并复核 |
| 将模型候选中的证据下标改为customer消息 | 不能据此认定客服违规 |
| 批量返回乱序 | 仍按ticket_id关联 |
| 批量缺少某条结果 | 该ID进入复核清单，total不减少 |
| 整批包含重复ID | 整批拒绝，不调用模型 |

这些场景已有本地代码测试；仍需验证平台变量连接和异常分支。

## 质量评估

eval_expected.json为人工构造参考答案，不是另一个模型打分。24+条样例覆盖分类、三项违规、安全提醒、客户自述与客服行为区分、多诉求、指令注入和输入不足。开发集小，只能用于本演示回归，不能推断生产分布准确率。

实际模型输出收集格式是最终result对象数组，不是开始节点参数，不是大模型原始候选。可从批量summary_json.results提取，另存为JSON数组。

运行：

```powershell
python tools/score_actual.py verification/actual_results.json
```

脚本只报告可判定字段的分类/规则/复核预期一致性，不代替人工检查语义。缺失样例计为未完成，不缩小总样本分母。不得把同一份预期答案直接作为actual_results评估。

证据存在性与语义支持性分开检查：代码能检查“原文存在、角色正确”，人工还要检查“这句原话是否真的支撑这个结论”。例如“不要把支付验证码发给任何人”虽然含验证码，但不构成索要。

## 3分钟演示顺序

1. 说明用途：复核售后客服对话，给出可核查的质检与分流建议。
2. 展示knowledge中的3项规则，解释是演示商家的自定义规则。
3. 运行single_normal：展示物流分类、当前未见违规及物流客服建议。
4. 运行single_violation：展示客服索取支付验证码的原文与R02条款。
5. 运行single_review：没有客服消息，输出人工复核而不是合规。
6. 运行batch_demo：展示总数、分类分布、违规项和待复核清单。
7. 展示一项错误注入，说明异常不会被当成“通过”。

## 简历与面试口径

只有平台运行与验收完成后，才使用“在Coze完成单条与批量工作流”的表述。当前仅有材料和本地节点验证时，应如实表述为“已完成规则、提示词及节点实现，正在Coze集成验证”。

可解释的技术点：固定检查三条规则而不依赖模型选择是否检索；结构化输出后再代码校验；引用同时绑定消息角色与下标；分类与规则结果分开；复核独立于是否违规；批量按记录ID归并。

边界：没有自动建单、真正人工审核台、真实客服数据评估、生产部署或性能测试。这些都不是本次已经完成的成果。
